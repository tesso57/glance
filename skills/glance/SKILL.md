# glance

モデルを作成・更新する依頼では以下の手順を使う。既存モデルのレビューのみが依頼された場合は読み取りと報告に限定し、成果物を更新しない。

## 必要な参照資料

対象に応じて、この SKILL.md と同じディレクトリから次の資料を read ツールで読む。複数に該当すればそれぞれ読む。該当しない資料を読む必要はない。

- Go の実装: [Go の勘所](references/go.md)
- TypeScript の実装: [TypeScript の勘所](references/typescript.md)
- Java の実装: [Java の勘所](references/java.md)
- DB・ストレージ・外部 API などを扱う場合: [外部状態の勘所](references/external-state.md)
- コンポーネントと状態図を一つの Web UI にまとめる場合は [Web UI の入力形式](references/overview.md) を使う。

glance は、人がエージェントとソフトウェアの状態・性質を理解し、設計を考えるための作業です。
操作の実装手順より先に、操作の前にありうる状態と、成功・失敗した後の状態や保証したい性質を考えてください。

## 調査と対話

- まず対象の目的、利用者がしたいこと、対象範囲を把握する。新規開発ではユーザーの要望を、既存コードではコードと文書を根拠にする。
- 既存コードは実際の呼び出しと状態の読み書きに根拠を付ける。動的ディスパッチ、外部サービス、並行性など追跡できない部分は不明とする。
- リポジトリ全体、指定された機能、Git の変更やブランチを扱える。Git を使う場合は実際のリポジトリと対象 ref を確認し、基準が不明なら推測で断定しない。
- 実現・把握したい状態と操作候補を示し、要求に対して不足がないか考える。操作の対象が一件か集合かを区別する。読み取り操作は、対象の状態変更がないことと返す結果を表現する。
- 操作ごとに、複数の操作前の状態と可能な成功・失敗の結果、その後に保証したい性質を示す。状態遷移図と必要に応じた制御フローを、理解に役立つ粒度で扱う。
- 要求と実装から確認できたこと、推測、提案、未決定事項を区別する。推測で未決定の動作を確定させない。重要な判断はユーザーと対話して詰める。
- モデルが要求やコードを完全に表すとは限らない。要求の網羅性や実装との一致を、モデルの検査だけで保証したと述べない。
- 既存コードを扱う場合は先に入り口と関連する実装を読み、状態の読取・更新と各分岐を根拠のファイルと行番号とともに整理する。新規開発ではコード上の事実を作らず、ユーザーの要望と未決定事項から考える。

## 成果物

ユーザーの作業ディレクトリの .glance/ に、以下の構成でモデルを保存し、対話の進行に応じて更新する。書き込み前に既存のファイルを読み、内容と対象を確認する。他のモデルやユーザーの既存ファイルを誤って上書きしない。対象が異なる、所有関係が分からない、または変更を安全に統合できない場合は、確認せず上書きせずにユーザーへ尋ねる。

- model.md: 対象・目的・利用者の意図、範囲、状態、操作候補、根拠と未決定事項、および目指す振る舞いを記す。操作ごとの前状態、成功・失敗の結果、成功後の性質を含め、理解に役立つ Mermaid 図を添える。操作の網羅性は要求との照合として扱う。
- dependencies.md: 複数コンポーネントの依存が設計に関わる場合、または依存関係を求められた場合に作る。実装の呼び出し・読み書きとビルド時の参照を区別し、依存する側から依存先へ矢印を引く。キューや共有 DB は実際の境界で示す。コンポーネント名はコードに合わせ、依存関係の根拠となるファイルを添え、model.md からリンクする。
- glossary.md: 図に登場する状態変数やドメイン用語の説明を Markdown で記す。見出しは図に実際に出る TLA+ 変数名と一致させ、コード・仕様で使われるドメイン名や読みやすい名称を説明文に含める。見出しに「図中ではひとまとめ」などの注釈を付けず、直下の説明文で、それが何を指すか、複数のものを図上でまとめた場合は何をまとめたものかを述べる。たとえば `runArtifacts` は「1回の計測で生成される測定値の CSV と診断レポートを図中でひとまとめにしたもの」と説明できる。実際の名前とモデル上の抽象・表示用の名前を区別し、根拠となるコード・仕様の位置と未確認事項を別々に示す。例は書き方の説明であり対象に存在すると決めつけない。内容や対象が異なる既存資料は読んで尊重し、安全に統合できない場合は勝手に上書きしない。モデルや図の変更に合わせて説明も維持する。
- baseline.md: 既存コードや指定された Git の基準から確認した比較元の振る舞い、根拠（ファイルや ref）、調査範囲と不明点。既存対象の分析や差分比較を依頼された場合は作成してよい。既存の比較元は勝手に置き換えず、基準の更新が必要ならユーザーに確認する。未設定の場合は不在を示す。
- Spec.tla と Spec.cfg: 議論に必要な範囲で TLA+ モデルと有限の TLC 設定を作る。Spec.tla のモジュール名は Spec とする。利用可能な TLA+ ツールで構文やモデルを検査できる形を目指し、どの性質と前提、有限範囲を表すかを model.md に併記する。未決定の仕様を仮定する場合は明記する。

更新先は上記の作業ファイル。過去の版を比較するときは `.glance/history/v番号/` のファイルを読み取る。版番号の割り当て、アーカイブと保存日時の記録は extension が担当する。

glossary.md は TLA+ の各変数の見出しと説明を用意し、根拠と未確認事項を別の段落にまとめる。モデル変数は状態の一部であり、操作や矢印のラベルとして自動表示されるとは限らない。現在値を表す変数と操作前の値を保存する補助変数を混同せず、前者は遷移後の状態にも表示されることを踏まえる。表示を確認できない場合は実際の図でどう見えるか断定しない。
glance chart --by は単一行の単純な値に対応する。意味を損なわず有限のスカラー値で表せる場合に限り利用を検討し、複合値が必要ならそのまま記述し、集約表示の制限を明記する。一回の操作が正常に終了するモデルでは、終了後に遷移がないことを TLC がデッドロックと報告しないよう、終了状態でのみ UNCHANGED vars を許すアクションを Next に含めるなど、終了の扱いを明示する。これは実際の不具合を隠すためにデッドロック検査を無差別に無効化することではない。検証環境が利用可能であれば TLC で構文と性質を実際に確認し、失敗時は原因を報告して修正できる範囲で修正する。利用できなければ未検証と明記する。

TLC は異なる種類の値を等値比較しようとして実行エラーになる場合がある。例えば結果の未実行状態に文字列、実行後に真偽値を混ぜて比較するのではなく、`"pending"`、`"true"`、`"false"` のような同種のモデル値で表すか、処理段階と真偽値を別の変数に分ける。抽象化の意味を説明に記す。

各アクションのすべての分岐で、すべての変数の次状態を指定する。`IF ... THEN ... ELSE ...` の後に共通の `UNCHANGED` などを続ける場合は条件式全体を括弧で囲むか、各分岐に明記し、片方の分岐だけに条件が入らないようにする。TLC で未指定の次状態というエラーが出たら、性質違反ではなくモデルの記述エラーとして扱う。

現状と提案、事実と仮定を混ぜず、比較元がある場合は状態・遷移の追加、削除、変更と未決定の差を人に説明する。Git 差分の対象を指定された場合は基準と比較対象を記録し、コードを変更せず読み取る。モデルの更新はユーザーの作業を妨げない範囲で行い、意図していない実装変更を行わない。

## 検証結果

TLA+ が記述できたことと、TLC のモデル検査が実行され成功したことは異なる。実行していない検査や証明について成功を主張しない。実行した場合は使ったモデル・設定、制約、結果、反例やエラーを記録し、失敗や未実行も明示する。TLC の成功は指定した有限モデルについての結果であり、実装の正しさや形式証明を意味しない。形式証明についても、実際に証明と検査を行った場合だけ結果を報告する。
