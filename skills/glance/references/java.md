# Java のコードから状態と性質をモデル化する

Java の対象コードを読むときに、この資料を使う。まず入口となるメソッド、呼び出し先、型、状態の読み書きを調べ、根拠のファイルと行を記す。以下の観点は対象に関係する場合に確認し、存在しない処理や仕様を追加しない。解析できない振る舞いと、モデル化しない範囲を明示する。

## 値、参照、呼び出し先

- 状態を表す enum、フィールド、定数、入力の検証を確認する。`null` を受け取り得るか、どこで検査し、参照すると何が起こるかをコードと呼び出し元から調べる。プリミティブ値と参照型、`Optional`、外部入力の変換はそれぞれ区別し、型やアノテーションだけで実行時に有効な値が保証されると決めつけない。
- 同じ mutable object や collection を複数の参照で共有する場合、代入と破壊的更新のどちらか、コピーが浅いか深いか、変更がどの参照に見えるかを確認する。必要に応じて、操作の途中で他者が観測できる変更を表す。
- interface、継承、依存性注入、プロキシを経由する呼び出しは、実際の実装や設定を追う。呼び出し先を特定できなければその副作用と失敗を未確認として残し、interface の名前だけから保証を推測しない。

## 返り値、例外、後始末

- return と checked / unchecked exception の各経路について、終了前に既に起きた状態変更と呼び出し元が受け取る結果を対応付ける。例外が発生しても既存の変更が自動的に戻るとは限らない。
- `catch` が例外を変換・回復するか、`finally` が return や throw の前にどんな状態変更を行うかを確認する。`finally` 自身の例外や return が、元の結果に影響する場合も区別する。
- `try-with-resources` の close が必要な副作用を持つ場合は、close の実行順と失敗、主例外と suppressed exception を確認する。省略する場合はモデルの範囲に記す。
- 一回の処理の正常終了をデッドロックと混同しない。TLC の終端状態の扱いは共通手順に従う。

## 並行処理と外部状態

- `synchronized`、`volatile`、lock、atomic、executor、future、割り込みが関係するかを確認する。共有状態の読み書き、同期によって保証される順序、待機・失敗・取消を、対象のコードとライブラリの契約に照らして記す。特定の実行順や公平性を根拠なく仮定しない。
- TLA+ の一遷移をどの操作単位として扱うかを明記する。複数の更新や I/O を一歩にまとめると、途中の失敗や他スレッドから見える状態を省くことになる。不要な詳細は、何を省いたか記して抽象化する。
- DB の transaction やフレームワークの宣言的な transaction は、実際の適用範囲と commit・rollback・例外処理を確認する。ネットワークやストレージの副作用まで同時に戻ると仮定しない。プロキシ等の適用条件が不明なら未確認とする。外部状態が関係する場合は [外部状態の勘所](external-state.md) も読む。

## モデルと検査の範囲

操作前の状態、成功・失敗後の状態と返り値・例外、守りたい性質を対象に合わせて表す。入力、呼び出し先、並行実行、外部依存、原子性、異常終了について、何を含め何を仮定・省略したかを示す。TLC の成功は有限モデルの設定範囲に関する結果であり、Java 実装がそのモデルと一致することの証明ではない。
