# Go のコードから状態と性質をモデル化する

Go の対象コードを読むときだけ、この資料を使う。まず対象の関数とその呼び出し先、型、実際の状態の読み書きを確認し、観測した事実にファイルと行を付ける。以下は確認すべき観点であり、対象に存在しない処理や仕様を勝手に追加する指示ではない。追跡できない箇所とモデルから省いた範囲を明示する。

## 値と更新

- 状態を表す型、定数、ゼロ値、引数の検証を調べる。`string` 等を基底とする独自型の定数は、型として取りうる値の全体を必ずしも限定しない。定数以外の値を除外するなら、検証済みという根拠かモデルの前提を記す。
- ポインタ、スライス、map、interface が参照する値を更新するときは、変更が呼び出し元や他の参照から見えるかを確認する。コピーと共有を区別し、別名参照を追えないときは未確認として残す。
- `nil` のポインタ、map、slice、channel、interface は利用方法により振る舞いが違う。interface 自体が nil か、nil のポインタを保持する非 nil interface かも必要に応じて区別する。到達可能性を確認し、nil を一律にエラーや正常値とみなさない。
- interface の呼び出し先は実装・依存性注入・呼び出し元をたどる。動的な実装や依存先を特定できなければ、その操作の効果は未確認としてモデルに明記する。

## 返り値、エラー、終了

- 成功・エラーの返り値と、各 return の前に既に変わった状態を対応付ける。エラーが返ったことだけから、状態が変更されていないと決めつけない。エラーが途中で wrap・変換・無視される場合も確認する。
- 到達可能な `panic` や nil 参照、`recover` を調べる。通常の `error` と panic は別の結果として扱う。panic がどこで回復されるかを未確認なら、通常のエラー応答になると決めつけない。
- `defer` は return 時や panic による巻き戻し時にも実行される。登録順と引数評価のタイミング、後始末・返り値や共有状態への変更を確認し、モデルの終了前に必要な効果を表す。
- 関数の正常終了とデッドロックを区別する。TLC における終了状態の扱いは共通手順に従い、実際の待機不具合を終端として隠さない。

## 並行処理と中断

- goroutine、channel、mutex、atomic、`select` や `context.Context` の取消・期限が対象に関係するか調べる。どの処理が共有状態を読み書きし、どの同期が順序を保証するかをコードに基づいて記す。
- 例えば goroutine が外部処理を開始する場合、関数の return がその完了を意味するとは限らない。モデルでは開始・完了・失敗を必要な粒度で区別し、待機や中断を表す範囲を記す。
- channel の送受信、クローズやバッファ、`select` の競合について、対象の仕様に必要な可能性だけを扱う。未解析の並行処理がある場合は不明として残し、特定の順序や公平性を勝手に仮定しない。
- TLA+ の一遷移を何の単位とするかを明記する。複数の Go 操作や I/O を根拠なく不可分の一歩にまとめると、途中の失敗や割り込みを見落とす。逆に不要な詳細は、何を省いたかを記して抽象化する。

## DB と外部副作用

- トランザクションを使う場合、どの DB 操作がそのトランザクション内か、commit・rollback と各エラーを確認する。ネットワーク呼び出しやストレージ更新が同じトランザクションの対象だと仮定しない。
- 途中の外部副作用、DB 失敗、取消や再試行で何が残りうるかを区別する。rollback や commit の結果が不明なときは、実装や利用ライブラリの根拠なしに最終状態を断定しない。詳細は外部状態の参照資料も使う。

## 小さな例

`Complete(t *Task)` が `t.Status == InProgress` の場合だけ `Done` を代入し `true` を返すなら、非 nil の単独呼び出しに限り「成功後は Done」「それ以外では false で状態を変更しない」を候補として確認できる。`*Task` の nil、他の status 値、並行更新を含めるかは呼び出し元と対象範囲で決め、未確認は記録する。コードの結果と、望ましい仕様の提案は分ける。
