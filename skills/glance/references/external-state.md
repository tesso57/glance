# 外部状態を含むモデルの勘所

対象の操作が DB、オブジェクトストレージ、外部 API、キューなどを読み書きするときに使う。まず実際の呼び出し先、順序、エラー処理と各サービスが保証する範囲をコードや設定で確認する。関係する状態を区別して表し、必要に応じて別の変数にして、操作後にそれぞれ何が残るかを考える。

## 境界と途中状態

- DB のトランザクションに含まれる操作と、含まれないネットワーク・ストレージ操作を区別する。`rollback` が外部の副作用を取り消すと仮定しない。
- 外部操作を呼ぶ前、成功後、後続操作の失敗後を調べる。エラー応答やタイムアウトは「外部側で何も起きなかった」とは限らない。完了・未実行・部分実行・結果不明のうち根拠のある可能性を表し、詳細が分からない場合は未確認と記す。
- DB の読み書きの範囲、commit / rollback の成否、タイムアウトやキャンセル時に呼び出し元が観測できる結果を調べる。実際の結果が分からない commit や rollback の失敗は、成功・失敗のどちらかと決めつけない。
- 一括削除や複数の更新がある場合は、全部成功・全部失敗だけでなく、途中まで成功する可能性が仕様や実装上あるか調べる。処理順と、状態ごとのエラー応答をモデルに反映する。

## 再試行と並行操作

- 再試行が実装されているか、失敗を呼び出し側に返すだけかを区別する。実装やサービス契約に根拠がある場合だけ、冪等性、重複呼び出し、補償処理や再試行による復旧をモデルに入れる。
- 並行するリクエスト、非同期処理、外部からの変更が対象の性質に影響するか確認する。重要な場合は中間状態と割り込み可能な境界をモデル化し、順序や可視性に未確認の保証を置かない。対象外にする場合は単独実行という前提を記す。
- 外部 API やキューについては、リクエスト送信、結果受信、相手側での状態変更を区別し、遅延・重複・順序・配信保証などを契約や実装で確認する。分からない保証は仮定または未確認として残す。

## モデルと報告

関係する外部状態、各遷移の前後、エラー時に残る状態、守りたい性質を記述する。根拠のない結果は確定せず、保守的に複数の可能性を含めるか、探索対象から外した理由と未確認事項を示す。初期状態、モデルの有限範囲、原子的とみなす操作、読み書きの観測範囲、前提を `model.md` に記す。

たとえば計測結果を登録する操作では、DB の記録と外部ストレージの測定データを別々の状態として表す。測定データの保存に成功した後、DB への登録に失敗する経路も検討する。DB の変更が取り消されるか、外部ストレージに何が残るかは、関連コードとサービスの契約を確認し、確かめられない場合は仮定として残す。

検査で反例が出たら、モデル内の経路とその前提を示し、実際のコードで起こりうるかを別途確かめる。TLC の結果だけで実装の不具合や正しさを断定しない。
