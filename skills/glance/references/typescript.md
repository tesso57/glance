# TypeScript のモデル化

対象の TypeScript / JavaScript コードを読み、以下の観点のうち実際に関係するものだけを使う。初めに関数や API の入口、呼び出し元、読み書きする状態を特定する。観測できた事実、モデルの抽象化、前提、未確認をファイルと行番号を添えて区別する。

## 型と実行時の境界

- union 型・enum・型注釈から候補を拾うが、型宣言だけで実行時入力が常にその値に限られるとは仮定しない。外部リクエスト、JSON、DB、JavaScript、`any`、型アサーションなどを経由する値は、実行時の検証や呼び出し元を確認する。
- `undefined`、`null`、未指定プロパティ、型外の値について、到達可能性と分岐・例外をコードから確認する。正規の型を満たす入力だけをモデル化するなら、境界検証の有無と、その前提を明記する。
- 型外の多数の値を `other` の一状態にまとめるのは、対象の操作で同じように扱われることを確認した場合に限る。条件によって挙動が異なる、または未調査なら、その違いを残す。

## 結果と途中の変更

- 正常な return、`throw`、Promise の resolve / reject と、それぞれの前に更新された状態を追う。例外でも更新が取り消されるとは限らない。`try` / `catch` / `finally` や呼び出し元が失敗を変換・回復する場合は、その境界まで確認する。
- たとえば `task.status = "done"; await save(task)` では、`save` の reject 時にメモリ上の値と保存先がどうなり得るかをそれぞれ調べる。保存先が変更されなかった、または元に戻ったと根拠なく決めない。
- 呼び出しを一つの遷移にまとめる場合は、途中の状態と失敗を省いてよい理由や前提を記す。戻り値の取得だけの操作は、状態の読み取りと出力の関係として記し、対象を変更したことにしない。

## 非同期処理と共有状態

- `await`、Promise の連鎖、タイマー、イベント、同時リクエストなどを調べ、待機中に別の処理が観察・変更できる状態があるか確認する。関連する場合は待機前後を別の遷移として扱う。`await` が一つあるだけで必ず競合するとは決めない。
- `Promise.all` の一つが reject しても、他の処理が自動的に取り消されたとは扱わない。各処理の完了・失敗と副作用を、コードや依存先から確認する。
- 参照を共有するオブジェクトの代入、破壊的更新、浅いコピーと深いコピーを区別する。どの参照から同じ状態を変更できるか追えない場合は未知と記す。プロパティへのアクセスが getter や proxy を経由する可能性など、関連する実行時の振る舞いは前提として切り分ける。

## 呼び出し先と外部状態

- 呼び出し先の実装、登録されたハンドラ、DB・ストレージ・外部 API の読み書きを必要な範囲でたどり、成功・失敗の返却と実際の副作用を区別する。動的ディスパッチや依存先が追えない場合は、分かったふりをせず未確認とする。
- DB、キャッシュ、ファイル、外部 API を含む場合は、それぞれをどの状態として表すか、更新の順序と原子性の根拠を確認する。トランザクションの外にある副作用は、DB のロールバックと同時に戻るとは限らない。

## モデルで確認すること

操作前にありうる状態、成功と失敗それぞれの操作後の状態、戻り値・例外、保証したい性質を対象に合わせて記述する。可能な入力範囲、非同期処理、外部依存、例外処理をどこまで含めたかを併記する。TLC の結果はその設定のモデルについての結果であり、TypeScript の型安全性や実装との一致を自動で保証しない。
