# 評価用の期待事項（エージェント入力に含めない）

前提は1件の注文を逐次処理し、各 map は初期化済みで、保存された Order の ID と検索キーが一致すること。状態を注文レコード・予約・通知回数として区別する。interface の任意実装や並行呼び出しに保証を広げない。

- `checkout.go` の Find が見つからないなら `ErrNotFound`、`paid` は即 `nil`、`pending` 以外は `ErrStatus`。これらは後続の予約・保存・通知を呼ばない。
- `Reserve` エラーでは先に返り、`fakes.go` の mock は更新前に失敗するので予約状態は変わらず、保存・通知も行わない。
- `Reserve` 成功後に `Save` が失敗した場合、注文は以前の `pending` のまま。`Release` が成功すれば予約を false にし、失敗なら予約は true のまま。`errors.Join` は保存エラーと解放エラーを伝える。通知は呼ばない。
- 保存成功後に通知が失敗した場合は注文は `paid`、予約は true、通知回数は増えず、エラーが返る。成功なら通知回数が1増えて `nil` を返す。
- 通知失敗後の同一注文の再試行は既に `paid` なので早期に `nil` を返し、通知を再送しない。この挙動を「通知済み」と誤認しない。
- 本データでは予約の初期状態を false と仮定する場合、その前提を明記する。`Find` は bool のみで失敗経路を持たず、任意 interface での部分成功や永続化の原子性を導入しない。
- 参照: `input/checkout.go` の条件・呼び出し順、`input/fakes.go` の失敗時の更新、`input/order.go` の値とエラー。TLC 成功は有限モデルについての結果であり、実装との一致の証明ではない。
